# Dynamic Compute Adaptation

Chloros
1.2.0 ใช้การตรวจจับฮาร์ดแวร์และการเลือกกลยุทธ์การประมวลผลอัตโนมัติ เครื่องยนต์การประมวลผลจะปรับตัวให้เหมาะสมกับฮาร์ดแวร์ของคุณ — ตั้งแต่ Jetson Orin Nano ไปจนถึงเวิร์กสเตชันที่มีหลาย GPU — โดยไม่ต้องตั้งค่าด้วยมือ

***

## วิธีทำงาน

เมื่อChloros
เริ่มต้นทำงาน มันจะวิเคราะห์ระบบของคุณ:

1. **ตรวจจับระบบปฏิบัติการ** —Windows
หรือLinux
2. **ระบุจำนวนคอร์ CPU และ RAM รวม**

3.**ตรวจจับการมีอยู่ของ GPU** — ความสามารถ NVIDIA CUDA, VRAM, รุ่น
4. **ระบุรุ่น Jetson** (หากมี) — ผ่าน `/proc/device-tree/model`
5. **ตรวจสอบเซ็นเซอร์อุณหภูมิ** (Jetson) — เพื่อการประมวลผลที่คำนึงถึงอุณหภูมิ
6. **เลือกกลยุทธ์การคำนวณ** — ตามอุปกรณ์ฮาร์ดแวร์ที่ตรวจพบทั้งหมด
7. **กำหนดจำนวนเวิร์กเกอร์ ประเภทไพพ์ไลน์ และการจัดสรรหน่วยความจำ** โดยอัตโนมัติ

โปรไฟล์ที่ตรวจพบจะถูกเก็บไว้ในแคชสำหรับเซสชันนี้ทั้งในหน่วยความจำและบนดิสก์ ทำให้การรันครั้งต่อไปเริ่มต้นได้เร็วขึ้น:

| แพลตฟอร์ม | โปรไฟล์ที่เก็บไว้ในแคช |
| --- | --- |
| **Linux
/ Jetson** | `~/.config/chloros/system_config.json` (ให้สิทธิ์ `XDG_CONFIG_HOME`) |
| **Windows** | `%LOCALAPPDATA%\Chloros\config\system_config.json` |

ลบไฟล์นั้นเพื่อบังคับให้ระบบตรวจจับใหม่ — มีประโยชน์หลังจากเพิ่ม GPU หรือ RAM เพิ่มเติมChloros
จะตรวจจับใหม่โดยอัตโนมัติเมื่อแคชถูกเขียนโดยเวอร์ชันเก่าที่ไม่เข้ากัน

## กลยุทธ์การประมวลผล

Chloros
จะเลือกหนึ่งในสามกลยุทธ์การประมวลผลตามฮาร์ดแวร์ของคุณ:

| กลยุทธ์ | เลือกเมื่อ | Workers | Executor | Pipeline |
| --- | --- | --- | --- | --- |
| **`GPU_PARALLEL`**| GPU CUDA ที่รายงาน**VRAM 12GB+**(บนหน่วยความจำรวมของ Jetson, ยังต้องการ RAM ที่แชร์รวมทั้งหมด 12GB+) | `min(4, VRAM ÷ 4GB)`, ขั้นต่ำ 2 —**จำกัดสูงสุดที่ 2 บน Jetson** | `ProcessPoolExecutor` (spawn) | `fused_gpu` |
| **`GPU_SINGLE`**| GPU CUDA ที่มี**VRAM 2-12GB**| 3 (I/O overlap; การเข้าถึง GPU ถูกจัดลำดับโดยเซมาฟอร์).**1 (แบบลำดับ) บน Jetson ที่มี RAM น้อยกว่า 12GB** | `ProcessPoolExecutor` (spawn); แบบลำดับภายในกระบวนการบน Jetson ที่มี RAM น้อย | `fused_gpu` / `tiled_gpu` |
| **`CPU_PARALLEL`** | ไม่มี GPU CUDA หรือ VRAM น้อยกว่า 2GB | `max(2, physical cores − 1)` | `ThreadPoolExecutor` | `cpu_fallback` |

ตัวอย่างการคำนวณสูตรจำนวน worker ของ `GPU_PARALLEL`: VRAM 12GB → 3 worker, 16GB ขึ้นไป → 4 worker, Jetson ทุกรุ่น → 2 worker.

การทำงานแบบขนานถูกนำไปใช้กับ `concurrent.futures` มาตรฐานของPython
: กลยุทธ์ GPU ใช้ `ProcessPoolExecutor` พร้อม **spawn** (แต่ละ worker เป็นกระบวนการแยกต่างหากที่มีบริบท CUDA ของตัวเอง — `fork` จะคัดลอกสถานะ CUDA ที่ได้รับการเริ่มต้นแล้วและทำให้กระบวนการลูกเสียหาย), ส่วนกลยุทธ์ CPU ใช้ `ThreadPoolExecutor`Chloros
ไม่ใช้เฟรมเวิร์กกระจายงานของบุคคลที่สามใดๆ (เช่น Ray)

### ประเภทของ Pipeline

* **`fused_gpu`** — เส้นทางการประมวลผล GPU แบบเต็มรูปแบบ การดำเนินการ Debayer, การแก้ไข และการจัดดัชนีทำงานบน GPU ในขั้นตอนเดียวที่รวมกัน มีอัตราผ่านข้อมูลสูงสุด แต่ต้องการ VRAM มากที่สุด
* **`tiled_gpu`** — เส้นทางการประมวลผล GPU ที่ประหยัดหน่วยความจำ ประมวลผลภาพเป็นไทล์เพื่อให้พอดีกับหน่วยความจำ GPU ที่จำกัด มีอัตราผ่านข้อมูลต่ำกว่า แต่ทำงานได้บนอุปกรณ์ที่มีข้อจำกัดด้านหน่วยความจำ
* **`cpu_fallback`** — การประมวลผลด้วย CPU เท่านั้น โดยใช้การทำงานแบบขนานหลายเธรด ใช้เมื่อไม่มี GPU ของ NVIDIA และเป็นตัวสำรองสุดท้ายเมื่อทั้งสองเส้นทาง GPU ล้มเหลว

ลำดับการสำรองในรันไทม์จะเป็น `fused_gpu` → `tiled_gpu` → `cpu_fallback` เสมอ

## การกำหนดกลยุทธ์ด้วยตนเอง

ตั้งค่าตัวแปรสภาพแวดล้อม `CHLOROS_STRATEGY` เพื่อบังคับใช้กลยุทธ์เฉพาะ — ทางออกสำหรับผู้เชี่ยวชาญเมื่อการตรวจจับอัตโนมัติเลือกตัวเลือกที่ไม่เหมาะสมกับสถานการณ์ของคุณ (เช่น การเก็บ GPU ไว้ว่างสำหรับงานอื่น):

```bash
# Valid values: CPU_PARALLEL, GPU_SINGLE, GPU_PARALLEL
CHLOROS_STRATEGY=CPU_PARALLEL chloros-cli process ~/datasets/flight001
```

ตัวแปรนี้ไม่แยกแยะตัวพิมพ์ใหญ่-เล็ก; สิ่งใดที่ไม่ใช่หนึ่งในสามชื่อดังกล่าวจะถูกเพิกเฉย และการตรวจจับอัตโนมัติจะดำเนินต่อไปตามปกติ เมื่อมีการกำหนดค่าทับซ้อน ระบบChloros
จะยังคงเลือกจำนวนผู้ทำงานให้คุณ:

| การกำหนดค่าทับซ้อน | จำนวนผู้ทำงานที่ใช้ |
| --- | --- |
| `CPU_PARALLEL` | `max(2, physical cores − 1)` |
| `GPU_SINGLE` | 3 |
| `GPU_PARALLEL` | `min(4, physical cores)` |

แนะนำให้ตั้งค่าตามคำสั่งแต่ละครั้งแทนที่จะตั้งค่าแบบถาวร เพื่อให้การทำงานปกติสามารถปรับตัวอัตโนมัติได้

## พฤติกรรมเฉพาะแพลตฟอร์ม

| แพลตฟอร์ม | กลยุทธ์ | จำนวน Worker | ท่อประมวลผล | หมายเหตุ |
| --- | --- | --- | --- | --- |
| **Jetson Orin Nano 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (แบบลำดับ) | โหมดประหยัดหน่วยความจำ, ดำเนินการภาพหนึ่งภาพต่อครั้ง |
| **Jetson Orin NX 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (แบบลำดับ) | RAM ที่ใช้ร่วมกันต่ำกว่า 12GB ทำให้ต้องประมวลผลแบบลำดับ |
| **Jetson Orin NX 16GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (พร้อมกัน) | อุปกรณ์ edge ที่แนะนำ — Jetson จำกัดไว้ที่ 2 workers |
| **Jetson AGX Orin 32-64GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (พร้อมกัน) | ประสิทธิภาพสูงสุดที่อุปกรณ์ edge (Jetson จำกัดไว้ที่ 2 workers เช่นกัน) |
| **เดสก์ท็อปที่มี GPU 8GB** | `GPU_SINGLE` | 3 | `fused_gpu` / `tiled_gpu` | 3 workers ทำงานทับซ้อนกันใน I/O ในขณะที่ semaphore จัดลำดับการเข้าถึง GPU |
| **เดสก์ท็อปที่มี GPU 12GB+** | `GPU_PARALLEL` | 3-4 | `fused_gpu` (พร้อมกัน) | ประสิทธิภาพเดสก์ท็อปที่เหมาะสมที่สุด: 12GB → 3 workers, 16GB+ → 4 |
| **ระบบใช้ CPU เท่านั้น** | `CPU_PARALLEL` | จำนวนคอร์ทางกายภาพ − 1 (ขั้นต่ำ 2) | `cpu_fallback` | ไม่ต้องการ GPU, ใช้กลุ่มเธรด |

{% hint style="info" %}
**หน่วยความจำรวมของ Jetson**: อุปกรณ์ Jetson ใช้หน่วยความจำของ GPU และ CPU ร่วมกัน Jetson Orin NX 16GB รายงาน VRAM ประมาณ 15.3GB แต่เป็น RAM ทางกายภาพเดียวกันที่ระบบปฏิบัติการและกระบวนการของ CPU ใช้ นั่นคือเหตุผลที่ Jetson 16GB+ มีคุณสมบัติตรงตามข้อกำหนดของ `GPU_PARALLEL` เช่นเดียวกับ GPU เดสก์ท็อป 12GB+ แต่ถูกจำกัดไว้ที่ 2 worker — GPU, กระบวนการ worker และบริบท CUDA ของแต่ละ worker ล้วนดึงข้อมูลจากพูลที่ใช้ร่วมกันเดียวกัน
{% endhint %}

### งบประมาณ GPU ตาม VRAM (GPU แยก)

บนโฮสต์ x86_64 ที่มี GPU แยกของ NVIDIA VRAM ที่ตรวจพบจะกำหนดด้วยว่าส่วนการประมวลผลของบัตรสามารถใช้พื้นที่ได้เท่าใด และขนาดของแบทช์สามารถขยายได้มากเพียงใด:

| VRAM ที่ตรวจพบ | ขีดจำกัดงบประมาณ GPU | ตัวคูณขนาดชุด |
| --- | --- | --- |
| **8GB+** | 90% | ×2.0 |
| **6-8GB** | 85% | ×1.75 |
| **

3.5-6GB** | 80% | ×1.5 |
| **2-3.5GB** | 75% | ×1.25 |
| **น้อยกว่า 2GB** | 70% | ×1.0 |

GPU แยกตัวจะสำรองพื้นที่เพียง 0.5GB สำหรับระบบ เนื่องจากไม่ใช้ RAM ของระบบร่วมกัน ส่วนโปรไฟล์ Jetson จะสำรองพื้นที่มากกว่ามาก แต่กำหนดขีดจำกัดไว้ต่ำกว่า — ดู [คู่มือ NVIDIA Jetson](../linux/nvidia-jetson-guide.md#per-model-gpu-budget)

## การจัดสรรหน่วยความจำ GPU แบบไดนามิก

Chloros
ใช้ [ท่อประมวลผล 4 เธรด](processing-pipeline.md):

* **เธรด 1** (การตรวจจับ) — การโหลดภาพ, การวิเคราะห์ EXIF, การตรวจจับเป้าหมาย
* **Thread 2** (การปรับเทียบ) — การคำนวณการปรับเทียบการสะท้อนแสง
* **Thread 3** (การประมวลผล) — การกำจัดเดย์เยอร์ด้วย GPU, การแก้ไขวิเนตต์, การคำนวณดัชนี
* **Thread 4** (การส่งออก) — การเขียนไฟล์, การฝังเมตาดาต้า

เธรด 1, 2 และ 4 ใช้ GPU น้อย ส่วนเธรด 3 เป็นเธรดที่ใช้ GPU มากที่สุด เมื่อเธรดในขั้นตอนก่อนหน้าเสร็จสิ้น งบประมาณ GPU ของพวกมันจะถูก **จัดสรรใหม่ให้กับเธรดที่ยังทำงานอยู่** ดังนั้น เธรด 3 จะได้รับหน่วยความจำเพิ่มขึ้นเรื่อยๆ ตามความคืบหน้าของการประมวลผล

### ขั้นตอนการจัดสรร

| ขั้นตอน | เธรดที่ทำงาน | การจัดสรรหน่วยความจำ GPU |
| --- | --- | --- |
| **ต้น** | 1, 2, 3, 4 | แบ่งให้ทุกเธรด โดยส่วนใหญ่ให้เธรด 3 |
| **กลาง-ต้น** | 2, 3, 4 | ส่วนของเธรด 1 ถูกจัดสรรใหม่ |
| **กลาง-ปลาย** | 3, 4 | ส่วนแบ่งของเธรด 1+2 ถูกโอนไปยัง 3+4 |
| **ปลาย** | 3 หรือ 4 | เธรดที่ยังทำงานอยู่สุดท้ายจะได้รับส่วนแบ่งสูงสุด |

มีสองกฎที่ควบคุมตัวเลขเหล่านี้:

* เธรดที่เป็น **เพียง** เธรดเดียวที่ยังทำงานอยู่ จะได้รับการจัดสรรสูงสุดตามโปรไฟล์ของมัน
* เมื่อมีงาน GPU *หนัก* มากกว่าหนึ่งงานที่ยังทำงานอยู่ การจัดสรรพื้นฐานของแต่ละงานหนักจะถูกแบ่งระหว่างงานเหล่านั้น (ไม่เคยต่ำกว่าค่าขั้นต่ำที่กำหนดไว้)

ค่าที่ใช้งานจริงในระหว่างการทำงานคือ **ค่าที่ต่ำกว่า** ระหว่างการจัดสรรของโปรไฟล์แพลตฟอร์มกับคำแนะนำแบบเรียลไทม์จากตัวตรวจสอบหน่วยความจำ GPU ดังนั้นการ์ดที่ทำงานหนักจะมีความสำคัญเหนือกว่าโปรไฟล์ที่ตั้งไว้แบบมองโลกในแง่ดีเสมอ***

## การประมวลผลที่คำนึงถึงเท็กซ์เจอร์

ตัว debayer ที่รับรู้เท็กซ์เจอร์ (**เฉพาะChloros
ขึ้นไป** — `--debayer texture-aware`) ทำงานด้วยโมเดลลดสัญญาณรบกวน AI/ML ที่ต้องการ VRAM ประมาณ 1.75GB ใน FP16 ต่อการคัดลอกหนึ่งครั้ง ดังนั้นจึงใช้หน่วยความจำ GPU มากกว่าวิธีการมาตรฐานอย่างมาก:

* ระบบที่มี **VRAM น้อยกว่า 7GB**จะประมวลผล Texture Aware ใน**วงจรแบบซิงโครนัส (synchronous loop) โดยประมวลผลภาพทีละภาพ** — ไม่สามารถใส่สำเนาโมเดลหลายชุดได้ และการใช้กลุ่มผู้ทำงาน (worker pool) จะยิ่งเพิ่มปัญหาการแย่งกันใช้ทรัพยากร
* ระบบที่มี **VRAM 7GB+** สามารถประมวลผล Texture Aware แบบพร้อมกันได้ แต่จำนวน worker จะลดลงเมื่อเทียบกับวิธี Standard
* บน **Jetson**, Texture Aware จะถูกกำหนดให้ทำงานกับ worker เดียวเสมอ และบนรุ่นที่ใช้พลังงานต่ำ (Nano, Orin Nano) ระบบจะตั้งค่าจำกัดความถี่ GPU โดยอัตโนมัติ — ดู [NVIDIA Jetson Guide](../linux/nvidia-jetson-guide.md#gpu-frequency-cap-for-texture-aware-on-nano-and-orin-nano)***

## การจัดการความร้อน (Jetson)

อุปกรณ์ Jetson มีข้อจำกัดด้านความร้อน โดยเฉพาะอย่างยิ่งในการติดตั้งในสภาพแวดล้อมที่ปิดหรือบนอากาศChloros
จะติดตามเซ็นเซอร์อุณหภูมิในตัวของ Jetson และปรับขนาดชุดงาน (batch size) โดยอัตโนมัติ:

| อุณหภูมิ | การตอบสนอง |
| --- | --- |
| **&lt; 70°C** | ทำงานปกติ — ความเร็วเต็ม |
| **70°C** (คำเตือน) | ขนาดชุดงานลดลงอย่างค่อยเป็นค่อยไป (100% → 50% ระหว่าง 70°C ถึง 80°C) |
| **80°C** (วิกฤต) | การลดความเร็วอย่างรุนแรง (50% → 0% ระหว่าง 80°C ถึง 90°C) |
| **90°C** (ปิดระบบ) | หยุดการประมวลผล GPU ทั้งหมด |

บนระบบเดสก์ท็อปที่มีระบบระบายความร้อนเพียงพอ การลดความเร็วเนื่องจากความร้อนจะเกิดขึ้นได้น้อยมาก

## การจัดการความกดดันของหน่วยความจำ

Chloros
จะตรวจสอบหน่วยความจำ GPU อย่างต่อเนื่องระหว่างการประมวลผล และตอบสนองในสามระดับ

**การกำหนดขนาดชุดงาน** ขนาดแบทช์เริ่มต้นที่ 8 ภาพ คูณด้วยตัวคูณแพลตฟอร์มจากตารางข้างต้นChloros
จากนั้นจะตรวจสอบ VRAM ที่ว่าง จอง 20% ของมันไว้สำหรับค่าใช้จ่ายของ PyTorch เอง และสมมติว่าใช้หน่วยความจำ GPU ประมาณ 100MB ต่อภาพ 12MP — ขนาดแบทช์จะเป็นค่าที่น้อยกว่า ระหว่างขีดจำกัดที่คำนวณจากหน่วยความจำหรือค่าพื้นฐานของแพลตฟอร์ม ขนาดแบตช์จะไม่ลดลงต่ำกว่า 1

**การลดขนาดแบบป้องกัน**เมื่อ**การใช้งาน VRAM เกิน 85%** ขนาดแบตช์จะถูกลดลงก่อนที่จะเกิดข้อผิดพลาดใดๆ**การตัดลดการจัดสรรต่อเธรด** เมื่อการใช้งานจริงเพิ่มขึ้น งบประมาณ GPU ของแต่ละเธรดจะถูกปรับลดลง: ×0.75 เมื่อการใช้งานเกิน 80%, ×0.5 เมื่อการใช้งานเกิน 90% ระดับการเฝ้าระวังคือ 70% (ระดับระมัดระวัง), 85% (ขีดจำกัดการทำงานปกติ), และ 95% (ความเสี่ยง OOM)**การลดความถี่และฟื้นฟูเมื่อเกิด OOM** หากเกิดเหตุการณ์ขาดหน่วยความจำ (OOM) ขึ้น:

* ขนาดชุดงานจะ **ลดลงครึ่งหนึ่ง** และลดลงครึ่งหนึ่งอีกครั้งในทุกครั้งที่เกิด OOM ติดต่อกัน — ชุดงานที่สำเร็จในแต่ละครั้งจะลดการลงโทษนี้ลงหนึ่งขั้น
* การจัดสรรหน่วยความจำของเธรดที่ทำงานอยู่จะถูกลดลงเหลือ 70% ของค่าปัจจุบัน และตัวจัดสรรจะเปลี่ยนไปใช้กลยุทธ์แบบระมัดระวัง ก่อนที่จะผ่อนคลายอีกครั้งหลังจากมีการจัดสรรที่สำเร็จต่อเนื่อง
* เมื่ออยู่ภายใต้ความกดดันอย่างรุนแรง ท่อประมวลผลจะเปลี่ยนจาก `fused_gpu` เป็น `tiled_gpu` และเปลี่ยนเป็น `cpu_fallback` เป็นทางเลือกสุดท้าย

**RAM ของโฮสต์ (Jetson).** ก่อนการประมวลผล เครื่องมือCLI
จะประมาณค่าความจำสูงสุดของโฮสต์จากจำนวนภาพและโหมด debayer ของคุณ และจะแจ้งเตือนหากความจำ RAM บวกกับพื้นที่ swap ที่สนับสนุนด้วยไฟล์มีแนวโน้มไม่เพียงพอ โดยพิมพ์คำสั่งที่แม่นยำเพื่อเพิ่มพื้นที่ swap — ดู [คู่มือ NVIDIA Jetson](../linux/nvidia-jetson-guide.md#swap-warning-and-recommendations).

## การติดตามการปรับตัวของระบบการคำนวณ

### การวินิจฉัยระบบ

`chloros-cli selftest` เป็นวิธีที่รวดเร็วที่สุดเพื่อยืนยันว่าชั้นการคำนวณเห็นอะไร:

```bash
chloros-cli selftest
```

การตรวจสอบ 7 รายการนี้ครอบคลุมเวอร์ชัน ความพร้อมใช้งานของพอร์ต การเริ่มต้นระบบหลังบ้าน `/api/test` ข้อมูลระบบ การมีอยู่ของโมเดลลดสัญญาณรบกวน และความพร้อมของ CUDA + โมเดลลดสัญญาณรบกวน การตรวจสอบที่ 5 จะพิมพ์บรรทัดข้อมูลฮาร์ดแวร์โดยตรง:

```
      GPU: NVIDIA RTX A4000, CUDA: True, PyTorch: 2.7.0
```

การตรวจสอบที่ 7 จะแสดง `CUDA: <bool>, Denoiser: <bool>` — ทั้งสองต้องเป็นจริงเพื่อให้ Texture Aware สามารถใช้งานได้เลย

### บันทึกของแบ็กเอนด์

กลยุทธ์และจำนวนผู้ทำงานจะถูกเลือกภายในแบ็กเอนด์เมื่อเริ่มต้นการรันแต่ละครั้ง — ไม่มีแบนเนอร์CLI
ที่ประกาศข้อมูลเหล่านี้ เมื่อมีสิ่งใดทำงานผิดปกติ (เช่น GPU path ที่ต้องใช้ทางเลือกสำรอง, OOM, หรือ denoiser ที่ไม่สามารถโหลดได้) บันทึกของ backend สำหรับเซสชันนั้นคือที่ที่ข้อมูลดังกล่าวจะปรากฏ:

| แพลตฟอร์ม | ตำแหน่งบันทึก |
| --- | --- |
| **Linux
/ Jetson** | `~/.cache/chloros/logs/backend_<YYYYMMDD_HHMMSS>.log` (ไฟล์หนึ่งต่อครั้งการเริ่มต้น) |
| **Linux
,CLI
-started backend** | `~/.chloros/backend.log` |
| **Windows** | `%LOCALAPPDATA%\Chloros\logs\` |

### ความคืบหน้าแบบเรียลไทม์

ระหว่างการรันCLI
จะแสดงความคืบหน้าแบบเรียลไทม์ต่อแต่ละเธรด (Detecting, Analyzing, Processing, Exporting) ที่ส่งผ่าน Server-Sent Events — ซึ่งเป็นข้อมูลสำคัญในการตรวจสอบว่าเธรด 3 เป็นจุดคอขวดหรือไม่ ดู [Processing Pipeline](processing-pipeline.md).
