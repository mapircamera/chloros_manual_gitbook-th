# การปรับแต่งการประมวลผลแบบไดนามิก

Chloros 1.3.0 ใช้การตรวจจับฮาร์ดแวร์และการเลือกกลยุทธ์การประมวลผลอัตโนมัติ เครื่องยนต์การประมวลผลจะปรับตัวให้เหมาะสมกับฮาร์ดแวร์ของคุณ — ตั้งแต่ Jetson Orin Nano ไปจนถึงเวิร์กสเตชันที่มีหลาย GPU — โดยไม่ต้องตั้งค่าด้วยมือ

***

## วิธีทำงาน

เมื่อChloros เริ่มทำงาน มันจะวิเคราะห์ระบบของคุณ:

1. **ตรวจหาระบบปฏิบัติการ** — Windows หรือ Linux
2. **ระบุจำนวนแกน CPU และ RAM รวม**

3.**ตรวจหาการมีอยู่ของ GPU** — ความสามารถ NVIDIA CUDA, VRAM, รุ่น
4. **ระบุรุ่น Jetson** (หากมี) — ผ่าน `/proc/device-tree/model`
5. **ตรวจสอบเซ็นเซอร์อุณหภูมิ** (Jetson) — เพื่อการประมวลผลที่คำนึงถึงอุณหภูมิ
6. **เลือกกลยุทธ์การประมวลผล** — โดยอิงจากฮาร์ดแวร์ทั้งหมดที่ตรวจพบ
7. **กำหนดจำนวน worker, ประเภท pipeline และการจัดสรรหน่วยความจำ** โดยอัตโนมัติ

โปรไฟล์ที่ตรวจพบจะถูกเก็บไว้ในแคชสำหรับเซสชันนี้ทั้งในหน่วยความจำและบนดิสก์ ทำให้การรันครั้งต่อไปเริ่มต้นได้เร็วขึ้น:

| แพลตฟอร์ม | โปรไฟล์ที่เก็บไว้ในแคช |
| --- | --- |
| **Linux / Jetson** | `~/.config/chloros/system_config.json` (ให้สิทธิ์ `XDG_CONFIG_HOME`) |
| **Windows** | `%LOCALAPPDATA%\Chloros\config\system_config.json` |

ลบไฟล์นั้นเพื่อบังคับให้ระบบตรวจจับใหม่ — มีประโยชน์หลังจากเพิ่ม GPU หรือ RAM เพิ่มเติม Chloros จะตรวจจับใหม่โดยอัตโนมัติเมื่อแคชถูกเขียนโดยเวอร์ชันเก่าที่ไม่เข้ากัน

***

## กลยุทธ์การคำนวณ

Chloros จะเลือกหนึ่งในสามกลยุทธ์การคำนวณตามฮาร์ดแวร์ของคุณ:

| กลยุทธ์ | เลือกเมื่อ | Worker | Executor | Pipeline |
| --- | --- | --- | --- | --- |
| **`GPU_PARALLEL`**| GPU CUDA ที่รายงาน**VRAM 12GB+**(บนหน่วยความจำรวมของ Jetson, ยังต้องการ RAM ที่แชร์รวมทั้งหมด 12GB+ ด้วย) | `min(4, ⌊(VRAM − 0.5GB) × 0.9 ÷ 3.5GB⌋)`, ขั้นต่ำ 2 —**จำกัดสูงสุดที่ 2 บน Jetson** | กระบวนการ Worker (บริบท CUDA แยกกัน) | `fused_gpu` |
| **`GPU_SINGLE`**| GPU CUDA ที่มี**VRAM 2-12GB**| 3 (I/O overlap; การเข้าถึง GPU ถูกจัดลำดับโดยเซมาฟอร์).**1 (แบบลำดับ) บน Jetson ที่มี RAM น้อยกว่า 12GB** | กระบวนการทำงาน (บริบท CUDA แยกกัน); แบบลำดับภายในกระบวนการบน Jetson ที่มี RAM น้อย | `fused_gpu` / `tiled_gpu` |
| **`CPU_PARALLEL`** | ไม่มี GPU CUDA หรือ VRAM น้อยกว่า 2GB | `max(2, physical cores − 1)` | `ThreadPoolExecutor` | `cpu_fallback` |

ตัวอย่างการคำนวณสูตรจำนวน worker ของ `GPU_PARALLEL`: VRAM 12GB → 2 worker, 16GB → 3 worker, 20GB+ → 4 worker. แต่ละ worker มีงบประมาณ 3.5GB ซึ่งเป็นความต้องการที่วัดได้ของงาน Texture Aware โดยอยู่ภายใน 90% ของ VRAM ที่เหลือหลังจากสำรอง 0.5GB

{% hint style="info" %}
**กลยุทธ์ GPU จำเป็นต้องใช้ PyTorch ที่สามารถใช้ CUDA ได้** เครื่องที่มี PyTorch แต่ไม่มีอุปกรณ์ CUDA ที่ใช้งานได้ จะได้รับ `CPU_PARALLEL` ไม่ว่า GPU ของมันจะเป็นอะไรก็ตาม แพ็กเกจ Jetson 1.3.0 ใช้ PyTorch ที่สร้างด้วย CUDA ของ JetPack 6 ดังนั้น Jetson จะผ่านเกณฑ์ทันทีที่ติดตั้งไลบรารี CUDA และ cuDNN ของ JetPack แล้ว Jetson ที่มี RAM น้อยกว่า 12GB จะประมวลผลภาพเพียงภาพเดียวในแต่ละครั้งภายในกระบวนการ (บันทึกเป็น `GPU_SINGLE`).
{% endhint %}

กลยุทธ์ GPU ทำงานโดยใช้กลุ่มของกระบวนการทำงาน (worker processes) ซึ่งแต่ละกระบวนการเป็นกระบวนการระบบปฏิบัติการ (OS process) แยกต่างหากที่มีบริบท CUDA ของตัวเอง โดยChloros จะเริ่มต้นกระบวนการนี้ด้วยการเรียกใช้โปรแกรมแบ็กเอนด์ที่ติดตั้งไว้ของตัวเองอีกครั้ง (ไม่ใช่ผ่าน `multiprocessing` ของPython ซึ่งการเริ่มต้นกระบวนการทำงาน (worker) ของมันไม่ทำงานภายในแอปพลิเคชันที่บรรจุในแพ็กเกจ) กลยุทธ์ CPU ใช้กลุ่มเธรด (`ThreadPoolExecutor` ของ Python) Chloros ไม่ใช้เฟรมเวิร์กการกระจายงานของบุคคลที่สามใดๆ (เช่น Ray)

### ประเภทของ Pipeline

* **`fused_gpu`** — เส้นทางการประมวลผล GPU แบบเต็มรูปแบบ การลบเดเบย์ การแก้ไข และการดำเนินการดัชนีทำงานบน GPU ในขั้นตอนเดียวที่ผสานรวมกัน มีอัตราผ่านข้อมูลสูงสุด แต่ต้องการ VRAM มากที่สุด
* **`tiled_gpu`** — เส้นทาง GPU ที่ประหยัดหน่วยความจำ. ประมวลผลภาพเป็นไทล์เพื่อให้พอดีกับหน่วยความจำ GPU ที่จำกัด. มีอัตราผ่านข้อมูลต่ำกว่า แต่ทำงานได้บนอุปกรณ์ที่มีหน่วยความจำจำกัด.
* **`cpu_fallback`** — การประมวลผลด้วย CPU เท่านั้น โดยใช้การประมวลผลแบบขนานหลายเธรด ใช้เมื่อไม่มี GPU ของ NVIDIA ให้ใช้งาน และเป็นทางเลือกสุดท้ายเมื่อทั้งสองเส้นทาง GPU ล้มเหลว

ลำดับการสำรองในรันไทม์จะเป็น `fused_gpu` → `tiled_gpu` → `cpu_fallback` เสมอ

## การกำหนดกลยุทธ์ด้วยตนเอง

ตั้งค่าตัวแปรสภาพแวดล้อม `CHLOROS_STRATEGY` เพื่อบังคับใช้กลยุทธ์เฉพาะ — ทางออกสำหรับผู้เชี่ยวชาญเมื่อการตรวจจับอัตโนมัติเลือกตัวเลือกที่ไม่เหมาะสมกับสถานการณ์ของคุณ (เช่น การเก็บ GPU ไว้ว่างสำหรับงานอื่น):

```bash
# Valid values: CPU_PARALLEL, GPU_SINGLE, GPU_PARALLEL
CHLOROS_STRATEGY=CPU_PARALLEL chloros-cli process ~/datasets/flight001
```

ตัวแปรนี้ไม่แยกแยะตัวพิมพ์ใหญ่-เล็ก; สิ่งใดที่ไม่ใช่หนึ่งในสามชื่อดังกล่าวจะถูกเพิกเฉย และระบบตรวจจับอัตโนมัติจะดำเนินการตามปกติ เมื่อมีการกำหนดค่าทับซ้อน Chloros จะยังคงเลือกจำนวน worker ให้คุณ:

| การกำหนดค่าทับซ้อน | จำนวน worker ที่ใช้ |
| --- | --- |
| `CPU_PARALLEL` | `max(2, physical cores − 1)` |
| `GPU_SINGLE` | 3 |
| `GPU_PARALLEL` | `min(4, physical cores)` |

การตั้งค่าทับ `GPU_SINGLE` หรือ `GPU_PARALLEL` บนเครื่องที่ไม่มีอุปกรณ์ CUDA ที่ใช้งานได้จะถูกปฏิเสธ พร้อมด้วยบรรทัด `[STRATEGY]` ในบันทึก, และกระบวนการทำงานจะใช้ `CPU_PARALLEL`

ควรตั้งค่าตามคำสั่งแต่ละครั้งแทนที่จะตั้งค่าแบบถาวร เพื่อให้กระบวนการทำงานปกติยังคงปรับตัวอัตโนมัติได้

## พฤติกรรมเฉพาะแพลตฟอร์ม

| แพลตฟอร์ม | กลยุทธ์ | ผู้ทำงาน | ท่อ | หมายเหตุ |
| --- | --- | --- | --- | --- |
| **Jetson Orin Nano 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (ลำดับ) | โหมดประหยัดหน่วยความจำ, หนึ่งภาพต่อครั้ง |
| **Jetson Orin NX 8GB** | `GPU_SINGLE` | 1 | `tiled_gpu` (แบบลำดับ) | RAM ที่ใช้ร่วมกันต่ำกว่า 12GB ทำให้ต้องประมวลผลแบบลำดับ |
| **Jetson Orin NX 16GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (พร้อมกัน) | อุปกรณ์ edge ที่แนะนำ — Jetson จำกัดไว้ที่ 2 workers |
| **Jetson AGX Orin 32-64GB** | `GPU_PARALLEL` | 2 | `fused_gpu` (พร้อมกัน) | ประสิทธิภาพสูงสุดสำหรับ edge (Jetson จำกัดไว้ที่ 2 workers) |
| **เดสก์ท็อปที่มี GPU 8GB** | `GPU_SINGLE` | 3 | `fused_gpu` / `tiled_gpu` | 3 workers overlap I/O while a semaphore serializes GPU access |
| **เดสก์ท็อปที่มี GPU 12GB+** | `GPU_PARALLEL` | 2-4 | `fused_gpu` (พร้อมกัน) | ประสิทธิภาพเดสก์ท็อปที่เหมาะสมที่สุด: 12GB → 2 workers, 16GB → 3, 20GB+ → 4 |
| **ระบบใช้ CPU เท่านั้น** | `CPU_PARALLEL` | จำนวนคอร์ทางกายภาพ − 1 (ขั้นต่ำ 2) | `cpu_fallback` | ไม่ต้องการ GPU, ใช้กลุ่มเธรด |

{% hint style="info" %}
**หน่วยความจำรวมของ Jetson**: อุปกรณ์ Jetson ใช้หน่วยความจำของ GPU และ CPU ร่วมกัน Jetson Orin NX 16GB รายงาน VRAM ประมาณ 15.3GB แต่เป็น RAM ทางกายภาพเดียวกันที่ใช้โดยระบบปฏิบัติการและกระบวนการของ CPU นั่นคือเหตุผลที่ Jetson 16GB+ มีคุณสมบัติตรงตามข้อกำหนดของ `GPU_PARALLEL` เช่นเดียวกับ GPU เดสก์ท็อป 12GB+ แต่ถูกจำกัดไว้ที่ 2 worker — GPU, กระบวนการ worker และบริบท CUDA ของแต่ละ worker ทั้งหมดใช้พูลที่แชร์ร่วมกันเดียวกัน
{% endhint %}

### งบประมาณ GPU ตาม VRAM (GPU แยก)

บนโฮสต์ x86_64 ที่มี GPU แยกของ NVIDIA, VRAM ที่ตรวจพบจะกำหนดด้วยว่าส่วนการประมวลผลของบัตรสามารถใช้พื้นที่ได้เท่าใด และขนาดของแบทช์สามารถขยายได้ใหญ่เพียงใด:

| VRAM ที่ตรวจพบ | ขีดจำกัดงบประมาณ GPU | ตัวคูณขนาดชุด |
| --- | --- | --- |
| **8GB+** | 90% | ×2.0 |
| **6-8GB** | 85% | ×1.75 |
| **

3.5-6GB** | 80% | ×1.5 |
| **2-3.5GB** | 75% | ×1.25 |
| **น้อยกว่า 2GB** | 70% | ×1.0 |

GPU แบบแยกตัว (Discrete GPUs) จัดสรรพื้นที่เพียง 0.5GB สำหรับระบบ เนื่องจากไม่ใช้ RAM ของระบบร่วมกัน ส่วนโปรไฟล์ Jetson จัดสรรพื้นที่มากกว่ามาก แต่กำหนดขีดจำกัดไว้ต่ำกว่า — ดู [คู่มือ NVIDIA Jetson](../linux/nvidia-jetson-guide.md#per-model-gpu-budget)

## การจัดสรรหน่วยความจำ GPU แบบไดนามิก

Chloros ใช้ [ท่อประมวลผล 4 เธรด](processing-pipeline.md):

* **เธรด 1** (การตรวจจับ) — การโหลดภาพ, การวิเคราะห์ EXIF, การตรวจจับเป้าหมาย
* **เธรด 2** (การปรับเทียบ) — การคำนวณการปรับเทียบการสะท้อนแสง
* **เธรด 3** (การประมวลผล) — การลบเดเบย์ด้วย GPU, การแก้ไขวิเนตต์, การคำนวณดัชนี
* **เธรด 4** (การส่งออก) — การเขียนไฟล์, การฝังเมตาดาต้า

เธรด 1, 2 และ 4 เป็นเธรดที่ใช้ GPU น้อย; Thread 3 เป็น thread ที่ใช้ GPU มากที่สุด เมื่อ thread ในขั้นตอนก่อนหน้าเสร็จสิ้น งบประมาณ GPU ของพวกมันจะถูก **จัดสรรใหม่ไปยัง thread ที่ยังทำงานอยู่** ดังนั้น Thread 3 จะได้รับหน่วยความจำเพิ่มขึ้นเรื่อยๆ ตามความคืบหน้าของการทำงาน

### ขั้นตอนการจัดสรร

| ขั้นตอน | Thread ที่ทำงานอยู่ | การจัดสรรหน่วยความจำ GPU |
| --- | --- | --- |
| **ต้น** | 1, 2, 3, 4 | แบ่งให้ทุกเธรด โดยส่วนใหญ่ให้เธรด 3 |
| **ต้น-กลาง** | 2, 3, 4 | ส่วนของเธรด 1 ถูกจัดสรรใหม่ |
| **กลาง-ปลาย** | 3, 4 | ส่วนแบ่งของเธรด 1+2 ถูกโอนไปยัง 3+4 |
| **ปลาย** | 3 หรือ 4 | เธรดที่ยังทำงานอยู่สุดท้ายจะได้รับส่วนแบ่งสูงสุด |

มีสองกฎที่ควบคุมตัวเลขเหล่านี้:

* เธรดที่เป็น **เพียง** เธรดเดียวที่ยังทำงานอยู่ จะได้รับการจัดสรรสูงสุดตามโปรไฟล์ของมัน
* เมื่อมีงาน GPU *หนัก* มากกว่าหนึ่งงานที่ยังทำงานอยู่ การจัดสรรพื้นฐานของแต่ละงานหนักจะถูกแบ่งระหว่างงานเหล่านั้น (ไม่เคยต่ำกว่าค่าขั้นต่ำที่กำหนดไว้)

ค่าที่ใช้จริงในระหว่างการทำงานคือ **ค่าที่ต่ำกว่า** ระหว่างการจัดสรรของโปรไฟล์แพลตฟอร์มกับคำแนะนำแบบเรียลไทม์จากตัวตรวจสอบหน่วยความจำ GPU ดังนั้นการ์ดที่ทำงานหนักจะชนะโปรไฟล์ที่ตั้งไว้แบบมองโลกในแง่ดีเสมอ***

## การประมวลผลที่คำนึงถึงเท็กซ์เจอร์

ตัว debayer ที่รองรับ Texture Aware (**เฉพาะ Chloros+** — `--debayer texture-aware`) ทำงานด้วยโมเดล AI/ML สำหรับการลดสัญญาณรบกวน ซึ่งต้องการ VRAM ประมาณ 1.75GB ใน FP16 ต่อการคัดลอกหนึ่งครั้ง ดังนั้นจึงใช้หน่วยความจำ GPU มากกว่าวิธีการมาตรฐานอย่างมาก:

* ระบบที่มี **VRAM น้อยกว่า 7GB**จะประมวลผล Texture Aware ใน**วงจรแบบซิงโครนัส ทีละภาพ** — ไม่สามารถใส่สำเนาโมเดลหลายชุดได้ และกลุ่มเวิร์กเกอร์จะยิ่งเพิ่มการแข่งขัน
* ระบบที่มี **VRAM 7GB+** สามารถประมวลผล Texture Aware แบบพร้อมกันได้ แต่จำนวน worker จะลดลงเมื่อเทียบกับวิธี Standard
* บน **Jetson**, Texture Aware จะถูกกำหนดให้ทำงานกับ worker เดียวเสมอ
* หาก **ไม่มี GPU CUDA ที่ใช้งานได้**, การรันจะใช้ debayer แบบ Standard และระบบหลังบ้านจะบันทึกบรรทัด `[DEBAYER] … needs a CUDA GPU …` หนึ่งบรรทัดเพื่ออธิบายเหตุผล
* บน Jetson ประหยัดพลังงาน (Nano, Orin Nano), CLI จะกำหนดขีดจำกัดความถี่ GPU เมื่อคุณร้องขอ Texture Aware — ดู [NVIDIA Jetson Guide](../linux/nvidia-jetson-guide.md#gpu-frequency-cap-for-texture-aware-on-nano-and-orin-nano)

***

## การจัดการความร้อน (Jetson)

อุปกรณ์ Jetson มีข้อจำกัดด้านความร้อน โดยเฉพาะอย่างยิ่งในการติดตั้งในสภาพแวดล้อมที่ปิดหรือบนอากาศ Chloros จะติดตามเซ็นเซอร์อุณหภูมิในตัวของ Jetson และปรับขนาดชุดงาน (batch size) โดยอัตโนมัติ:

| อุณหภูมิ | การตอบสนอง |
| --- | --- |
| **< 70°C** | ทำงานปกติ — ความเร็วเต็ม |
| **70°C** (คำเตือน) | ขนาดชุดงานลดลงอย่างค่อยเป็นค่อยไป (100% → 50% ระหว่าง 70°C ถึง 80°C) |
| **80°C** (วิกฤต) | การลดความเร็วอย่างรุนแรง (50% → 0% ระหว่าง 80°C ถึง 90°C) |
| **90°C** (ปิดระบบ) | หยุดการประมวลผล GPU ทั้งหมด |

บนระบบเดสก์ท็อปที่มีระบบระบายความร้อนเพียงพอ การลดความเร็วเนื่องจากความร้อนจะเกิดขึ้นได้น้อยมาก

***

## การจัดการความกดดันของหน่วยความจำ

Chloros ติดตามหน่วยความจำ GPU อย่างต่อเนื่องระหว่างการประมวลผล และตอบสนองในสามระดับ

**การกำหนดขนาดชุดงาน** ขนาดแบทช์เริ่มต้นที่ 8 ภาพ คูณด้วยตัวคูณแพลตฟอร์มจากตารางข้างต้น Chloros จะตรวจสอบ VRAM ที่ว่าง จากนั้นสำรอง 20% ของ VRAM นั้นไว้สำหรับค่าใช้จ่ายของ PyTorch เอง และสมมติว่าภาพ 12MP ใช้หน่วยความจำ GPU ประมาณ 100MB — ขนาดแบทช์จะเป็นค่าที่น้อยกว่า ระหว่างขีดจำกัดที่คำนวณจากหน่วยความจำหรือค่าพื้นฐานของแพลตฟอร์ม ขนาดแบตช์จะไม่ลดลงต่ำกว่า 1

**การลดขนาดแบบป้องกัน**เมื่อ**การใช้งาน VRAM เกิน 85%** ขนาดแบตช์จะถูกลดลงก่อนที่จะเกิดข้อผิดพลาดใดๆ**การปรับลดการจัดสรรต่อแต่ละเธรด** เมื่อการใช้งานจริงเพิ่มขึ้น งบประมาณ GPU ของแต่ละเธรดจะถูกปรับลดลง: ×0.75 เมื่อการใช้งานเกิน 80%, ×0.5 เมื่อการใช้งานเกิน 90% ช่วงการเฝ้าระวังของตัวตรวจสอบคือ 70% (ระดับระมัดระวัง), 85% (ขีดจำกัดการทำงานปกติ), และ 95% (ความเสี่ยง OOM)**การลดความถี่และฟื้นฟูเมื่อเกิด OOM** หากเกิดเหตุการณ์ขาดหน่วยความจำ (OOM) ขึ้น:

* ขนาดชุดงานจะ **ลดลงครึ่งหนึ่ง** และลดลงครึ่งหนึ่งอีกครั้งในทุกครั้งที่เกิด OOM ต่อเนื่อง — ชุดงานที่สำเร็จในแต่ละครั้งจะลดการลงโทษนี้ลงหนึ่งขั้น
* การจัดสรรหน่วยความจำของเธรดที่ทำงานอยู่จะถูกลดลงเหลือ 70% ของค่าปัจจุบัน และตัวจัดสรรจะเปลี่ยนไปใช้กลยุทธ์แบบระมัดระวัง โดยจะผ่อนคลายอีกครั้งหลังจากมีการจัดสรรที่สำเร็จต่อเนื่อง
* เมื่ออยู่ภายใต้ความกดดันอย่างรุนแรง ท่อประมวลผลจะเปลี่ยนจาก `fused_gpu` เป็น `tiled_gpu` และเปลี่ยนเป็น `cpu_fallback` เป็นทางเลือกสุดท้าย

**RAM ของโฮสต์ (Jetson).** ก่อนการประมวลผล CLI จะประมาณค่าความจำสูงสุดของโฮสต์จากจำนวนภาพและโหมด debayer และจะแจ้งเตือนหาก RAM บวกกับพื้นที่ swap ที่สนับสนุนด้วยไฟล์มีแนวโน้มไม่เพียงพอ พร้อมพิมพ์คำสั่งที่แม่นยำเพื่อเพิ่มพื้นที่ swap — ดู [คู่มือ NVIDIA Jetson](../linux/nvidia-jetson-guide.md#swap-warning-and-recommendations)

## การตรวจสอบการปรับแต่งระบบประมวลผล

### การวินิจฉัยระบบ

`chloros-cli selftest` เป็นวิธีที่เร็วที่สุดเพื่อยืนยันสิ่งที่ชั้นประมวลผลเห็น:

```bash
chloros-cli selftest
```

การตรวจสอบ 7 รายการนี้ครอบคลุมเวอร์ชัน ความพร้อมใช้งานของพอร์ต การเริ่มต้นระบบแบ็กเอนด์ `/api/test` ข้อมูลระบบ การมีอยู่ของโมเดลเดนอยเซอร์ และความพร้อมของ CUDA + เดนอยเซอร์ การตรวจสอบที่ 5 จะแสดงข้อมูลฮาร์ดแวร์โดยตรง:

```
      GPU: NVIDIA RTX A4000, CUDA: True, PyTorch: 2.7.0
```

การตรวจสอบที่ 7 จะแสดง `CUDA: <bool>, Denoiser: <bool>` — ทั้งสองต้องเป็นจริงเพื่อให้ Texture Aware สามารถใช้งานได้เลย

### บันทึกของแบ็กเอนด์

กลยุทธ์และจำนวน worker จะถูกเลือกภายใน backend เมื่อเริ่มต้นการรันแต่ละครั้ง — ไม่มีข้อความแจ้งเตือนในCLI ที่แสดงข้อมูลเหล่านี้ เมื่อเกิดปัญหาที่ไม่คาดคิด (เช่น GPU path ที่ต้องใช้ทางเลือกสำรอง, OOM, หรือ denoiser ที่ไม่สามารถโหลดได้) บันทึกของ backend สำหรับเซสชันนั้นจะเป็นที่ที่แสดงข้อมูลดังกล่าว:

| แพลตฟอร์ม | ตำแหน่งบันทึก |
| --- | --- |
| **Linux / Jetson** | `~/.cache/chloros/logs/backend_<YYYYMMDD_HHMMSS>.log` (ไฟล์หนึ่งต่อครั้งการเริ่มต้น) |
| **Linux, backend ที่เริ่มต้นผ่าน CLI** | `~/.chloros/backend.log` เช่นกัน |
| **Windows** | `%LOCALAPPDATA%\Chloros\logs\` |

### ความคืบหน้าแบบเรียลไทม์

ระหว่างการรัน โปรแกรมCLI จะแสดงความคืบหน้าแบบเรียลไทม์ของแต่ละเธรด (Detecting, Analyzing, Processing, Exporting) ที่ส่งผ่าน Server-Sent Events — ซึ่งเป็นข้อมูลสำคัญในการตรวจสอบว่าเธรด 3 เป็นจุดคอขวดหรือไม่ ดู [Processing Pipeline](processing-pipeline.md).
