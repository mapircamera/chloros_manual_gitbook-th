## สถาปัตยกรรม Pipeline

```

Images In → [Thread 1: Detection] → [Thread 2: Calibration] → [Thread 3: Processing] → [Thread 4: Export] → Files Out
```

ภาพทุกภาพจะไหลผ่านทั้งสี่เธรดตามลำดับ ด้วยระบบประมวลผลแบบหลายเธรดของChloros+ ภาพหลายภาพสามารถใช้เธรดต่าง ๆ พร้อมกันได้ — ในขณะที่เธรด 3 กำลังประมวลผลภาพหนึ่ง ภาพถัดไปอาจถูกตรวจจับโดยเธรด 1 ภาพอีกภาพอาจถูกปรับเทียบโดยเธรด 2 และภาพที่เสร็จแล้วอาจถูกเขียนลงดิสก์โดยเธรด 4

ความคืบหน้าถูกรายงานตามแต่ละเธรดและส่งผ่าน Server-Sent Events (ระบบหลังบ้านเผยแพร่ข้อมูลเหล่านี้บน `/api/events`) ในหน้าจอแสดงความคืบหน้าแบบเรียลไทม์ของCLI ทั้งสี่ขั้นตอนถูกระบุด้วย **Detecting, Analyzing, Processing, Exporting**

***

## รายละเอียดของ Thread

### Thread 1: การตรวจจับ

**วัตถุประสงค์**: โหลดภาพและตรวจจับเป้าหมายการปรับเทียบ

* อ่านไฟล์ภาพจากดิสก์ — คู่ไฟล์Survey3 `.raw`+`.jpg`, ภาพที่ถ่ายด้วย LATTICE `.tif`/`.tiff` และ `.dng`
* สกัดข้อมูลเมตาดาต้า EXIF (GPS, รุ่นกล้อง, เวลา, การเปิดรับแสง)
* ตรวจจับเป้าหมายการปรับเทียบ: รูปทรงเป้าหมายที่มีเครื่องหมาย ArUco สำหรับภาพที่ถ่ายด้วย LATTICE และแผงตรวจจับแบบคลาสสิกสำหรับภาพเป้าหมายการปรับเทียบของSurvey3
* ผลลัพธ์: ข้อมูลภาพ + เมตาดาต้า + ผลลัพธ์การตรวจจับเป้าหมาย

เป็นเธรดที่ขึ้นอยู่กับ I/O และ CPU เป็นหลัก

### Thread 2: การปรับเทียบ

**วัตถุประสงค์**: คำนวณพารามิเตอร์การปรับเทียบจากเป้าหมายที่ตรวจพบ

* คำนวณสัมประสิทธิ์การปรับเทียบการสะท้อนจากภาพเป้าหมาย
* คำนวณพารามิเตอร์การแก้ไข vignette
* กำหนดเส้นโค้งการปรับเทียบต่อแต่ละแถบ
* ผลลัพธ์: พารามิเตอร์การปรับเทียบสำหรับภาพแต่ละภาพ

เธรดการคำนวณที่ขึ้นอยู่กับ CPU เป็นหลัก ในการรันแบบSurvey3 หรือแบบผสม เธรด 3 จะรอจนกว่าการปรับเทียบการสะท้อนแสงจะเสร็จสิ้น ดังนั้นสัมประสิทธิ์การปรับเทียบจะพร้อมใช้งานก่อนที่ภาพใดๆ จะถูกประมวลผล ในการรันแบบ LATTICE เท่านั้น เธรด 3 จะทำงานระหว่างการตรวจจับ: แต่ละเฟรมจะเริ่มทำงานเมื่อจุดยึดเป้าหมายของเฟรมนั้นถูกกำหนดอย่างสมบูรณ์ เฟรมหนึ่งจะเลือกเป้าหมายที่ใกล้ที่สุดตามเวลาจากทั้งสองด้าน ดังนั้นมันจะรอจนกว่าทุกเฟรมของกล้องที่ใกล้กว่าเป้าหมายที่ใกล้ที่สุดปัจจุบันจะถูกสแกน ผลลัพธ์ที่ได้จะเหมือนกัน แต่ได้เร็วกว่า

### Thread 3: การประมวลผล (GPU)

**วัตถุประสงค์**: ปรับแก้และคำนวณดัชนีพืชพรรณ**นี่คือเธรดที่ใช้การคำนวณมากที่สุด**

* **Debayering**: แปลงข้อมูล RAW Bayer เป็นภาพหลายช่องสัญญาณ
  * มาตรฐาน (เร็ว, คุณภาพปานกลาง) — ค่าเริ่มต้น, `--debayer standard`
  * Texture Aware (ช้า, คุณภาพสูงสุด) — เฉพาะChloros+ เท่านั้น, `--debayer texture-aware`, ใช้โมเดลลดสัญญาณรบกวนด้วย AI/ML
  * การถ่ายภาพ LATTICE mono (M3M) เป็นภาพช่องเดียว: ขั้นตอนการถอดโมเสกและการปรับสมดุลสีขาวจะถูกข้ามไป (พร้อมข้อความบันทึกหนึ่งบรรทัด) ในขณะที่ภาพ M3C/Bayer ใด ๆ ในการรันเดียวกันยังคงได้รับการประมวลผลตามขั้นตอนดังกล่าว
* **การแก้ไข vignette**: ใช้การแก้ไข vignette ของเลนส์ทั่วทั้งภาพ
* **การปรับเทียบค่าสะท้อน**: ใช้สัมประสิทธิ์การปรับเทียบเพื่อแปลงเป็นค่าสะท้อน
* **การคำนวณดัชนี**: คำนวณดัชนีพืชพรรณ (NDVI, NDRE, GNDVI, …)
* ผลลัพธ์: ข้อมูลภาพที่ผ่านการประมวลผลแล้ว พร้อมสำหรับการส่งออก

เธรดนี้ได้รับประโยชน์สูงสุดจากการเร่งความเร็วด้วย GPU และเป็นเธรดที่ [Dynamic Compute Adaptation](dynamic-compute-adaptation.md) ปรับแต่ง

### Thread 4: ส่งออก

**วัตถุประสงค์**: เขียนภาพที่ผ่านการประมวลผลลงดิสก์

* เขียนไฟล์ผลลัพธ์ในรูปแบบที่เลือก — `TIFF (16-bit)`, `TIFF (8-bit)`, `TIFF (32-bit, Percent)`, `PNG (8-bit)`, `JPG (8-bit)`
* แทรกข้อมูลเมตาดาต้าลงในไฟล์ผลลัพธ์ (GPS, เวลาประทับ, พารามิเตอร์การประมวลผล) — รวมถึงแท็กการประมวลผล `Chloros:*` ซึ่งตั้งแต่เวอร์ชัน 1.3.0 จะถูกเขียนในทุกโหมดการประมวลผล ทั้งสำหรับ Survey3 และ LATTICE
* จัดระเบียบไฟล์ผลลัพธ์ภายใต้โฟลเดอร์โครงการเป็น `<camera>/<format>/<Product>_Images/` — เช่น `LATT-M3M-L41-F550/tiff16/Reflectance_Calibrated_Images/` **ไฟล์ที่ส่งออกจะรักษาชื่อไฟล์ต้นฉบับไว้; โฟลเดอร์จะระบุผลิตภัณฑ์**
* สำหรับการจับภาพ LATTICE, เฟรมต้นฉบับหนึ่งสามารถแตกออกเป็นผลิตภัณฑ์หลายชนิด (Debayered, Preview, Radiance, Reflectance, Index) โดยแต่ละผลิตภัณฑ์จะอยู่ในโฟลเดอร์ผลิตภัณฑ์ของตัวเอง ผลิตภัณฑ์ Index ถูกคำนวณจากผลิตภัณฑ์ reflectance ที่การรันได้เขียนไว้ (หากไม่มี จะคำนวณจากผลิตภัณฑ์อื่นที่การรันได้เขียนไว้ เช่น radiance) ผลิตภัณฑ์ Radiance และ reflectance ของกล้อง M3C แบบมัลติสเปกตรัมยังสามารถมีมาสก์จำกัดค่าต่อพิกเซลใน `<format>/clamp_masks/` (ดู [รูปแบบภาพผลลัพธ์](../output-image-formats.md#clamp-masks))
* ผลลัพธ์: ไฟล์สุดท้ายบนดิสก์

เป็นหลักเป็นเธรดที่จำกัดโดย I/O — การใช้พื้นที่จัดเก็บข้อมูล SSD จะช่วยปรับปรุงประสิทธิภาพได้อย่างชัดเจน

## เบื้องหลัง: Executors

ภายในเธรด 3 การทำงานต่อภาพแต่ละภาพถูกทำให้เป็นแบบขนานดังต่อไปนี้:

* **กลยุทธ์ GPU**(`GPU_SINGLE`, `GPU_PARALLEL`) ใช้**กลุ่มกระบวนการทำงาน** (worker processes) ซึ่งแต่ละกระบวนการเป็นกระบวนการระบบปฏิบัติการที่แยกกันและมีบริบท CUDA ของตัวเอง Chloros เริ่มต้นแต่ละ worker โดยเรียกใช้โปรแกรม backend ที่ติดตั้งไว้เองอีกครั้ง — ไม่ใช่ผ่าน `multiprocessing` ของ Python ซึ่งการเริ่มต้น worker ของมันไม่ทำงานภายในแอปพลิเคชันที่แพ็กเกจไว้
* **`CPU_PARALLEL`** ใช้กลุ่มเธรด (`ThreadPoolExecutor` ของ Python) — NumPy และ OpenCV ปล่อย GIL ออกไป ดังนั้นการใช้เธรดเพียงอย่างเดียวก็เพียงพอ
* อุปกรณ์ Jetson ที่มี RAM ร่วมกัน 8GB หรือน้อยกว่าจะข้ามตัวดำเนินการ (executor) ไปทั้งหมด และประมวลผลภายในกระบวนการแบบลำดับ
* Texture Aware บน GPU ที่มี VRAM น้อยกว่า 7GB ก็ทำงานแบบลำดับเช่นกัน — โมเดลลดสัญญาณรบกวน (denoiser) ไม่สามารถปรับให้พอดีได้มากกว่าหนึ่งครั้ง

Chloros ไม่ใช้เฟรมเวิร์กแบบกระจายของบุคคลที่สามใดๆ (เช่น Ray) ดู [Dynamic Compute Adaptation](dynamic-compute-adaptation.md) เพื่อทราบวิธีการเลือกกลยุทธ์และจำนวน worker

## การประมวลผลแบบลำดับกับการประมวลผลแบบท่อ

### โหมดฟรี (แบบลำดับ)

ในเวอร์ชันฟรีของChloros ภาพจะถูกประมวลผล **ทีละภาพ** ตามลำดับผ่านทั้งสี่ขั้นตอน:

```

Image 1: [Detect] → [Calibrate] → [Process] → [Export]
                                                         Image 2: [Detect] → [Calibrate] → [Process] → [Export]
```

GUI แสดงแถบความคืบหน้าที่เรียบง่ายในโหมดฟรี; ขั้นตอนแบบลำดับจะแสดงเป็น **Target Detection**และตามด้วย**Processing**.

### โหมดChloros+ (แบบท่อ)

ด้วยใบอนุญาตChloros+ สレッドทั้งสี่จะทำงาน **พร้อมกัน** บนภาพต่าง ๆ:

```

Thread 1: [Image 1] [Image 2] [Image 3] [Image 4] ...
Thread 2:           [Image 1] [Image 2] [Image 3] ...
Thread 3:                     [Image 1] [Image 2] ...
Thread 4:                               [Image 1] ...
```

แถบความคืบหน้าใน GUI แสดงทั้งสี่ขั้นตอน; นำเมาส์ไปวางเหนือแถบเพื่อดูความคืบหน้าของแต่ละเธรด ในCLI ทั้งสี่ขั้นตอนเดียวกันจะแสดงแบบเรียลไทม์เป็น **Detecting, Analyzing, Processing, Exporting**
{% hint style="info" %}
**หนึ่งป้ายกำกับ สองชื่อ** CLI เรียกขั้นตอนที่ 3 ว่า _Processing_ ส่วนข้อมูลความคืบหน้าในโหมดพรีเมียมของระบบหลังบ้าน — ซึ่งเป็นข้อมูลที่แถบความคืบหน้าของ GUI แสดง — ระบุขั้นตอนเดียวกันว่า _Calibrating_ ทั้งสองเป็นเธรดเดียวกันที่ทำงานเดียวกัน (เธรด 3: debayer, การแก้ไข, ดัชนี)
{% endhint %}

{% hint style="success" %}
**การประมวลผลแบบท่อ (Pipelined processing) ด้วย Chloros+** สามารถเร็วกว่าการประมวลผลแบบลำดับ (sequential processing) ได้ 3-5 เท่า ขึ้นอยู่กับฮาร์ดแวร์และขนาดชุดข้อมูลของคุณ ความเร็วจะเพิ่มขึ้นสูงสุดบนระบบที่มี GPU และ SSD ที่เร็ว
{% endhint %}

## ความคืบหน้าการส่งออกของ Thread 4

Thread การส่งออกมีระบบติดตามความคืบหน้าของตัวเอง ซึ่งคุณสามารถตรวจสอบได้แยกต่างหาก:**CLI:**

```bash
chloros-cli export-status
```

**SDK:**

```python
status = chloros.get_status()
print(f"Export: {status['export']['percent']}% - Phase: {status['export']['phase']}")
```

การประมวลผลจะเสร็จสิ้นเมื่อ Thread 4 ถึง 100%

{% hint style="info" %}
**การรันที่ไม่เขียนภาพใดเลยถือว่าล้มเหลว**เมื่อสำเร็จ `chloros-cli process` จะรายงานจำนวนผลิตภัณฑ์ภาพที่เขียน (`Image products written: N`) หากมีการร้องขอผลิตภัณฑ์แต่**ไม่มี**ผลิตภัณฑ์ใดถูกเขียน — มีเพียง `project.json` และ `calibration_data.json` — CLI จะพิมพ์ `Processing finished but wrote no image products.` และ**ออกด้วยค่าที่ไม่เท่ากับศูนย์**, โดยระบุชื่อโฟลเดอร์โครงการและสาเหตุทั่วไป (โฟลเดอร์อินพุตไม่ถูกรับรู้ว่าเป็นข้อมูลการจับภาพ — ตรวจสอบการจัดวางและ `--input-level` — หรือผลิตภัณฑ์ทุกชิ้นที่ขอมาไม่สามารถใช้ได้กับกล้องเหล่านั้น) สคริปต์สามารถใช้รหัสออกเป็นข้อมูลอ้างอิงได้
{% endhint %}

## ความสัมพันธ์กับการปรับแต่งการคำนวณแบบไดนามิก

[การปรับแต่งการคำนวณแบบไดนามิก](dynamic-compute-adaptation.md) มีผลกระทบหลักต่อ **Thread 3 (การประมวลผล)**:

* **`GPU_PARALLEL`**: Thread 3 ประมวลผลภาพหลายภาพผ่าน GPU พร้อมกันโดยใช้ท่อส่งข้อมูล `fused_gpu`
* **`GPU_SINGLE`**: Thread 3 จัดลำดับการเข้าถึง GPU แบบอนุกรมด้วยเซมาฟอร์ ในขณะที่กระบวนการทำงาน (worker processes) ดำเนินการ I/O แบบทับซ้อนกัน โดยใช้ `fused_gpu` หรือท่อประมวลผล `tiled_gpu` ที่ประหยัดหน่วยความจำ
* **`CPU_PARALLEL`**: Thread 3 ใช้การประมวลผลบน CPU พร้อมความขนานแบบหลายเธรด

การจัดสรรหน่วยความจำ GPU ของ Thread 3 ยังเพิ่มขึ้นเมื่อ Thread 1 และ 2 เสร็จสิ้น — ดู [การจัดสรรหน่วยความจำ GPU แบบไดนามิก](dynamic-compute-adaptation.md#dynamic-gpu-memory-allocation).
