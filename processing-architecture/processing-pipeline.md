## สถาปัตยกรรม Pipeline

```

Images In → [Thread 1: Detection] → [Thread 2: Calibration] → [Thread 3: Processing] → [Thread 4: Export] → Files Out
```

ภาพทุกภาพจะไหลผ่านทั้งสี่เธรดตามลำดับ ด้วยระบบประมวลผลแบบหลายเธรดของ Chloros+ ภาพหลายภาพสามารถใช้เธรดต่าง ๆ พร้อมกันได้ — ในขณะที่เธรด 3 กำลังประมวลผลภาพหนึ่ง ภาพถัดไปอาจถูกตรวจจับโดยเธรด 1 ภาพอีกภาพอาจถูกปรับเทียบโดยเธรด 2 และภาพที่เสร็จสมบูรณ์อาจถูกเขียนลงดิสก์โดยเธรด 4

ความคืบหน้าถูกรายงานตามแต่ละเธรดและส่งผ่าน Server-Sent Events (ระบบหลังบ้านเผยแพร่ข้อมูลเหล่านี้บน `/api/events`) ในหน้าจอแสดงความคืบหน้าแบบเรียลไทม์ของCLI ทั้งสี่ขั้นตอนถูกระบุเป็น **Detecting, Analyzing, Processing, Exporting**

***

## รายละเอียดของเธรด

### เธรด 1: การตรวจจับ

**วัตถุประสงค์**: โหลดภาพและตรวจจับเป้าหมายการปรับเทียบ

* อ่านไฟล์ภาพจากดิสก์ — คู่ไฟล์Survey3`.raw`+`.jpg`, ภาพที่ถ่ายด้วย LATTICE `.tif`/`.tiff` และ `.dng`
* สกัดข้อมูลเมตาดาต้า EXIF (GPS, รุ่นกล้อง, เวลา, การเปิดรับแสง)
* ตรวจจับเป้าหมายการปรับเทียบ: รูปทรงเป้าหมายที่มีเครื่องหมาย ArUco สำหรับภาพที่ถ่ายด้วย LATTICE และแผงตรวจจับแบบคลาสสิกสำหรับภาพเป้าหมายการปรับเทียบของSurvey3
* ผลลัพธ์: ข้อมูลภาพ + เมตาดาต้า + ผลลัพธ์การตรวจจับเป้าหมาย

เป็นเธรดที่ผูกกับ I/O และ CPU เป็นหลัก

### เธรด 2: การปรับเทียบ

**วัตถุประสงค์**: คำนวณพารามิเตอร์การปรับเทียบจากเป้าหมายที่ตรวจพบ

* คำนวณสัมประสิทธิ์การปรับเทียบการสะท้อนจากภาพเป้าหมาย
* คำนวณพารามิเตอร์การแก้ไข vignette
* กำหนดเส้นโค้งการปรับเทียบต่อแต่ละแถบ
* ผลลัพธ์: พารามิเตอร์การปรับเทียบสำหรับแต่ละภาพ

เป็นเธรดการคำนวณที่ขึ้นอยู่กับ CPU เป็นหลัก เธรด 3 จะรอผลจากเธรดนี้เมื่อการปรับเทียบการสะท้อนถูกเปิดใช้งาน เพื่อให้สัมประสิทธิ์พร้อมใช้งานก่อนที่ภาพใดจะถูกประมวลผล

### Thread 3: การประมวลผล (GPU)

**วัตถุประสงค์**: ดำเนินการแก้ไขและคำนวณดัชนีพืช**นี่คือ thread ที่ใช้การคำนวณมากที่สุด*** **Debayering**: แปลงข้อมูล RAW Bayer เป็นภาพหลายช่องสัญญาณ
  * มาตรฐาน (เร็ว, คุณภาพปานกลาง) — ค่าเริ่มต้น, `--debayer standard`
  * Texture Aware (ช้า, คุณภาพสูงสุด) — เฉพาะChloros+ เท่านั้น, `--debayer texture-aware`, ใช้โมเดลลดสัญญาณรบกวนด้วย AI/ML
  * การถ่ายภาพ LATTICE mono (M3M) เป็นภาพช่องเดียว: ขั้นตอนการเดโมเซอิกและการปรับสมดุลสีขาวจะถูกข้ามไปสำหรับภาพเหล่านี้ (พร้อมข้อความบันทึกหนึ่งบรรทัด) ในขณะที่ภาพ M3C/Bayer ใด ๆ ในการรันเดียวกันยังคงได้รับการประมวลผลตามขั้นตอนดังกล่าว
* **การแก้ไข vignette**: ใช้การแก้ไข vignette ของเลนส์ทั่วทั้งภาพ
* **การปรับเทียบค่าสะท้อน**: ใช้สัมประสิทธิ์การปรับเทียบเพื่อแปลงเป็นค่าสะท้อน
* **การคำนวณดัชนี**: คำนวณดัชนีพืชพรรณ (NDVI, NDRE, GNDVI, …)
* ผลลัพธ์: ข้อมูลภาพที่ผ่านการประมวลผลและพร้อมสำหรับการส่งออก

เธรดนี้ได้รับประโยชน์สูงสุดจากการเร่งความเร็วด้วย GPU และเป็นเธรดที่ [Dynamic Compute Adaptation](dynamic-compute-adaptation.md) ปรับแต่ง

### เธรด 4: ส่งออก

**วัตถุประสงค์**: เขียนภาพที่ประมวลผลแล้วลงดิสก์

* เขียนไฟล์ผลลัพธ์ในรูปแบบที่เลือก — `TIFF (16-bit)`, `TIFF (32-bit, Percent)`, `PNG (8-bit)`, `JPG (8-bit)`
* แทรกข้อมูลเมตาดาต้าลงในไฟล์ผลลัพธ์ (GPS, เวลาประทับ, พารามิเตอร์การประมวลผล)
* จัดเรียงไฟล์ผลลัพธ์ไว้ในโฟลเดอร์โครงการภายใต้ชื่อ `<camera>/<format>/<Product>_Images/` — เช่น `LATT-M3M-L41-F550/tiff16/Reflectance_Calibrated_Images/`. **ไฟล์ที่ส่งออกจะรักษาชื่อไฟล์ต้นฉบับไว้; โฟลเดอร์จะระบุชื่อผลิตภัณฑ์**
* สำหรับการจับภาพ LATTICE, เฟรมต้นฉบับหนึ่งสามารถแตกออกเป็นผลิตภัณฑ์หลายชนิด (Debayered, Preview, Radiance, Reflectance, Index), โดยแต่ละชนิดอยู่ในโฟลเดอร์ผลิตภัณฑ์ของตัวเอง
* ผลลัพธ์: ไฟล์สุดท้ายบนดิสก์

เป็นหลักเป็นเธรดที่จำกัดโดย I/O — การใช้ SSD จะช่วยปรับปรุงประสิทธิภาพได้อย่างชัดเจน

## เบื้องหลัง: Executors

ภายในเธรด 3 การทำงานต่อภาพแต่ละภาพถูกทำให้ทำงานแบบขนานด้วย `concurrent.futures` มาตรฐานของPython:

* **กลยุทธ์ GPU**(`GPU_SINGLE`, `GPU_PARALLEL`) ใช้ `ProcessPoolExecutor` พร้อม**spawn** — แต่ละเธรดทำงานเป็นกระบวนการแยกต่างหากที่มีบริบท CUDA ของตัวเอง (`fork` จะรับสภาวะ CUDA ที่ถูกกำหนดค่าเริ่มต้นจากกระบวนการแม่มา และทำให้สภาวะของกระบวนการลูกเสียหาย)
* **`CPU_PARALLEL`** ใช้ `ThreadPoolExecutor` — NumPy และ OpenCV ปล่อย GIL ออกไป ดังนั้นการใช้เธรดก็เพียงพอแล้ว
* อุปกรณ์ Jetson ที่มี RAM ร่วมกัน 8GB หรือน้อยกว่า จะข้าม executor ไปทั้งหมด และประมวลผลภายในกระบวนการแบบลำดับ
* Texture Aware บน GPU ที่มี VRAM น้อยกว่า 7GB ก็ทำงานแบบลำดับเช่นกัน — โมเดล denoiser ไม่สามารถปรับให้พอดีได้มากกว่าหนึ่งครั้ง

Chlorosไม่ใช้เฟรมเวิร์กกระจายงานของบุคคลที่สามใดๆ (เช่น Ray) ดู [Dynamic Compute Adaptation](dynamic-compute-adaptation.md) เพื่อทราบวิธีการเลือกกลยุทธ์และจำนวน worker

## การประมวลผลแบบลำดับกับการประมวลผลแบบท่อ

### โหมดฟรี (แบบลำดับ)

ในเวอร์ชันฟรีของ Chloros ภาพจะถูกประมวลผล **ทีละภาพ** ตามลำดับผ่านทั้งสี่ขั้นตอน:

```

Image 1: [Detect] → [Calibrate] → [Process] → [Export]
                                                         Image 2: [Detect] → [Calibrate] → [Process] → [Export]
```

GUI แสดงแถบความคืบหน้าที่เรียบง่ายในโหมดฟรี; ขั้นตอนแบบลำดับจะแสดงเป็น **Target Detection**และตามด้วย**Processing**.

### โหมด Chloros+ (แบบท่อ)

ด้วยใบอนุญาต Chloros+ ทั้งสี่เธรดจะทำงาน **พร้อมกัน** บนภาพต่าง ๆ:

```

Thread 1: [Image 1] [Image 2] [Image 3] [Image 4] ...
Thread 2:           [Image 1] [Image 2] [Image 3] ...
Thread 3:                     [Image 1] [Image 2] ...
Thread 4:                               [Image 1] ...
```

แถบความคืบหน้าใน GUI แสดงสี่ขั้นตอน; นำเมาส์ไปวางเหนือแถบเพื่อดูความคืบหน้าของแต่ละเธรด ใน CLI สี่ขั้นตอนเดียวกันจะแสดงแบบเรียลไทม์เป็น **Detecting, Analyzing, Processing, Exporting**{% hint style="info" %}**หนึ่งป้ายชื่อ สองชื่อ** CLI เรียกขั้นตอนที่ 3 ว่า _Processing_ ส่วนฟีดความคืบหน้าในโหมดพรีเมียมของระบบหลังบ้าน — ซึ่งเป็นข้อมูลที่แถบความคืบหน้าของ GUI แสดง — ระบุขั้นตอนเดียวกันว่า _Calibrating_ ทั้งสองเป็นเธรดเดียวกันที่ทำงานเดียวกัน (Thread 3: debayer, corrections, indices).
{% endhint %}

{% hint style="success" %}
**การประมวลผลแบบท่อ (Chloros+)** สามารถเร็วกว่าการประมวลผลแบบลำดับได้ 3-5 เท่า ขึ้นอยู่กับฮาร์ดแวร์และขนาดชุดข้อมูลของคุณ ความเร็วจะเพิ่มขึ้นสูงสุดบนระบบที่มี GPU และ SSD ที่เร็ว
{% endhint %}

## ความคืบหน้าการส่งออกของ Thread 4

Thread การส่งออกมีระบบติดตามความคืบหน้าของตัวเอง ซึ่งคุณสามารถตรวจสอบได้แยกต่างหาก:**CLI:**

```bash
chloros-cli export-status
```

**SDK:**

```python
status = chloros.get_status()
print(f"Export: {status['export']['percent']}% - Phase: {status['export']['phase']}")
```

การประมวลผลจะเสร็จสิ้นเมื่อ Thread 4 ถึง 100%

{% hint style="info" %}
**การรันที่ไม่เขียนภาพใดเลยถือว่าล้มเหลว**เมื่อสำเร็จ `chloros-cli process` จะรายงานจำนวนผลิตภัณฑ์ภาพที่เขียน (`Image products written: N`) หากมีการร้องขอผลิตภัณฑ์แต่**ไม่มี**ผลิตภัณฑ์ใดถูกเขียน — มีเพียง `project.json` และ `calibration_data.json` — โปรแกรม CLI จะพิมพ์ `Processing finished but wrote no image products.` และ**ออกจากระบบด้วยค่าที่ไม่ใช่ศูนย์**, โดยระบุชื่อโฟลเดอร์โครงการและสาเหตุทั่วไป (โฟลเดอร์อินพุตไม่ถูกรับรู้ว่าเป็นข้อมูลที่จับภาพ — ตรวจสอบการจัดวางและ `--input-level` — หรือผลิตภัณฑ์ทุกชิ้นที่ร้องขอไม่สามารถใช้ได้กับกล้องเหล่านั้น) สคริปต์สามารถพึ่งพารหัสการออกได้
{% endhint %}

## ความสัมพันธ์กับ Dynamic Compute Adaptation

[Dynamic Compute Adaptation](dynamic-compute-adaptation.md) มีผลหลักต่อ **Thread 3 (Processing)**:

* **`GPU_PARALLEL`**: Thread 3 ประมวลผลภาพหลายภาพผ่าน GPU พร้อมกันโดยใช้ท่อส่งข้อมูล `fused_gpu`
* **`GPU_SINGLE`**: Thread 3 จัดลำดับการเข้าถึง GPU แบบอนุกรมด้วยเซมาฟอร์ ในขณะที่กระบวนการทำงาน (worker processes) ดำเนินการ I/O แบบทับซ้อนกัน โดยใช้ `fused_gpu` หรือท่อประมวลผล `tiled_gpu` ที่ประหยัดหน่วยความจำ
* **`CPU_PARALLEL`**: Thread 3 ใช้การประมวลผลบน CPU พร้อมความขนานแบบหลายเธรด

การจัดสรรหน่วยความจำ GPU ของ Thread 3 ยังเพิ่มขึ้นเมื่อ Thread 1 และ 2 เสร็จสิ้น — ดู [การจัดสรรหน่วยความจำ GPU แบบไดนามิก](dynamic-compute-adaptation.md#dynamic-gpu-memory-allocation).
